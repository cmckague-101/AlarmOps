## Design specificity verdict

**LLM assessment:** FireOps has credible product-specific language and records: apparatus types, VINs, VIPR checklists, DOT inspections, credentials, assignments, and operational issue states. Status-led lists fit dispatch and fleet work. Composition remains familiar admin-dashboard territory, though. Generic stat cards, side navigation, drawers, and activity rows could support many inventory products with copy swapped.

**Deterministic scan:** Detector returned zero findings for `src/App.tsx`. It did not catch contextual and workflow defects below because they depend on product data and interaction logic rather than markup anti-patterns.

**Visual overlays:** Browser automation unavailable in this session, and no Chromium executable or installed Playwright/Puppeteer runtime was found. No reliable user-visible overlay exists.

## Overall impression

Solid operational foundation. Interface scans well and treats statuses as real work, not decoration. Biggest opportunity is contextual trust: users need to know which vehicle they are acting on, whether changes are saved, and which company receives an invitation.

## What's working

- Vehicle and issue rows combine identity, state, assignment, and issue count in one scan path.
- Drawers use labelled dialogs, focus trapping, Escape handling, focus restoration, and mobile back controls.
- Role-aware navigation and empty states keep unavailable actions out of member workflows.

## Priority issues

### [P1] Issue detail loses vehicle context

**Why it matters:** `IssueDetail` receives `vehicle` but never renders it. A mechanic reviewing "Pump losing pressure" cannot verify unit, model, or current status before adding notes or resolving it. This creates wrong-vehicle risk.

**Fix:** Put unit name, vehicle type/model, and current vehicle status directly below issue title. Keep context visible near update and resolve actions.

**Suggested command:** `/impeccable harden`

### [P1] Save state is invisible and operational changes lack recovery

**Why it matters:** Data saves after a 300 ms debounce, but users see no saving or saved state. Vehicle status and assignment update instantly without undo. On a weak field connection, users can leave believing changes persisted.

**Fix:** Add persistent `Saving`, `Saved`, and `Save failed` status. Retry failed saves. Add short-lived Undo for status and assignment changes, or require confirmation for out-of-service transitions.

**Suggested command:** `/impeccable harden`

### [P1] Invitation copy names wrong company

**Why it matters:** Invite drawer hardcodes "North Ridge Wildfire." Real tenants can send an invitation showing another company's name, damaging trust and causing access confusion.

**Fix:** Pass current company into `InviteCrewForm` and render its actual name. Confirm recipient and company in success feedback.

**Suggested command:** `/impeccable clarify`

### [P2] Expert fleet work remains one-record-at-a-time

**Why it matters:** Users cannot sort, batch-update, bulk-assign, or filter issues by priority or vehicle. As fleet size grows, routine reviews become repeated drawer interactions.

**Fix:** Add sort and compact filter controls, multi-select for safe bulk actions, and keyboard-accessible list navigation. Keep novice path unchanged.

**Suggested command:** `/impeccable distill`

### [P2] Long forms expose too much at once and lose unfinished work

**Why it matters:** Add Vehicle presents eight document decisions in one section. On mobile, interruption closes work with no draft. This raises cognitive load for field users.

**Fix:** Collapse optional documents behind "Add documents," save form drafts locally, and restore interrupted work. Keep basic vehicle details first.

**Suggested command:** `/impeccable adapt`

## Cognitive load

Moderate, with three checklist failures. Document upload section exceeds four visible decisions. Owner mobile navigation exposes five top-level choices. Issue detail creates a memory bridge because vehicle context disappears. Grouping, hierarchy, and drawer-based progressive disclosure otherwise work.

## Emotional journey

Arrival is calm and competent. Status chips and Needed actions create useful urgency without alarm. Emotional valley appears at high-stakes state changes: interface offers no explicit save reassurance or undo. End states rely on brief toast messages, so confidence fades once toast disappears.

## Persona red flags

**Alex, power user:** Fleet and issue reviews require opening records one at a time. No sorting, bulk actions, shortcuts, or persistent filters. Ten recent actions cap history without a route to full activity.

**Sam, accessibility-dependent user:** Dialog focus handling, labels, visible focus, and live toast region are strong. Save-in-progress state is never announced. Status changes rely on transient feedback and have no accessible undo path.

**Casey, distracted mobile user:** Bottom navigation and floating actions sit in thumb reach. Add Vehicle is long, optional uploads dominate the flow, and unfinished input disappears when drawer closes or page reloads.

## Minor observations

- `Updated now` is static copy, not actual recency.
- Crew invitation supports optional name, then derives display name from email. Confirmation should show derived name before sending.
- Company page is read-only but does not explain where owners edit business details.
- Help score is zero: no support contact, definitions for VIPR/DOT terms, or guidance for status transitions.

## Questions to consider

- Should issue resolution optimize for speed, or require stronger unit verification before changing state?
- Is FireOps meant for fleets of 5 to 20 vehicles, or hundreds? Current interaction model fits smaller fleets.
- Which matters more in field conditions: immediate optimistic updates or explicit saved-state certainty?
