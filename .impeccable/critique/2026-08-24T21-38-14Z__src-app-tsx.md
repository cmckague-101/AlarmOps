## Design specificity verdict

**LLM assessment.** Authored for FireOps, not generic fleet software. Terms such as "Type 3 Engine," "VIPR Checklist," "Red Card," and "out of service" give product credibility. Dense operational rows, explicit issue counts, and ember rarity form coherent visual language.

Composition remains familiar admin software: fixed sidebar, stat strip, bordered lists, right drawers. Product character comes mostly from vocabulary and palette. Stronger operational prioritization could make dashboard feel like field command software rather than themed fleet CRUD.

**Deterministic scan.** Detector returned zero findings for `src/App.tsx`. No rule names or file locations. Scan missed source-level concerns below: 8–10px metadata, contradictory status state, hidden error location, and competing mobile actions.

**Visual overlays.** No reliable user-visible overlay. Browser automation and mutable page injection unavailable in current tool set.

## Overall impression

Good discipline. Interface knows its domain and avoids decorative dashboard noise. Biggest opportunity: turn record management into operational decision support. Current UI records fleet state well, but does less to prevent impossible states or speed urgent work.

Cognitive load is moderate, with two checklist failures. Add-vehicle form exposes six document uploads plus registration fields in one long drawer, so progressive disclosure and minimal choices fail. Main lists and dashboard chunk information well.

Emotional journey works at completion points through save state, toasts, undo, and "All caught up." Valley occurs after long-form submit. User can remain at footer while error sits far above, with no focus shift or summary.

## What's working

- Domain language is unusually specific. Vehicle types, credentials, inspections, assignments, and issue severity match real operating concepts.
- Status communication is redundant in good way. Text, icons, semantic color, counts, and issue labels avoid color-only meaning.
- Interaction foundation is sound. Drawers trap focus, close with Escape, restore focus, mark background inert, announce saves, preserve form data, and support undo.

## Priority issues

### [P1] Status and assignment can contradict each other

**Why it matters.** Owner can set vehicle to "Assigned" without selecting crew member. Unassigning crew can also leave vehicle status as "Assigned." Fleet roster then presents impossible operational state.

**Fix.** Treat assignment as one transaction. Selecting "Assigned" must require assignee. Clearing assignee should require next status, defaulting to "Ready." Show both fields in one control group and validate invariant before save.

**Suggested command:** `/impeccable harden`

### [P1] Long forms hide validation failures above viewport

**Why it matters.** Add-vehicle drawer ends after many optional uploads. Submit at bottom can fail because "Unit name" near top is empty, but user receives no summary and focus stays at footer.

**Fix.** Focus and scroll first invalid field after submit. Add compact error summary at form top with links. Keep field-level errors.

**Suggested command:** `/impeccable audit`

### [P1] Operational text drops below practical reading size

**Why it matters.** Issue priority, status, timestamps, vehicle metadata, activity details, and crew details use 8–10px text. Field users on phones, sunlight, zoom, or low vision will miss task-critical facts.

**Fix.** Set 12px floor for metadata and 11px only for low-priority labels. Increase line-height and spacing instead of shrinking information to fit. Verify both themes at 200% zoom.

**Suggested command:** `/impeccable typeset`

### [P2] Mobile Fleet screen has two competing floating actions

**Why it matters.** "New issue" and "Add vehicle" occupy opposite bottom corners above navigation. Both claim primary-action weight, reduce usable viewport, and compete with bottom-nav targets.

**Fix.** Keep "New issue" as persistent field action. Move "Add vehicle" into page heading or one labeled action menu for owners. Preserve 44px separation from navigation.

**Suggested command:** `/impeccable distill`

### [P2] Dashboard lacks direct action paths and expert tools

**Why it matters.** Dashboard identifies urgent records but cannot create issue, add vehicle, filter action list, or process several records. Owners must navigate away before acting.

**Fix.** Add one role-aware primary action and compact shortcuts for issue creation and fleet intake. Add bulk handling only where repeated actions are real.

**Suggested command:** `/impeccable layout`

## Persona red flags

**Alex, power user.** Can open urgent records quickly, but no keyboard shortcuts, command search, bulk status updates, or saved fleet filters exist. Recent actions show only ten items with no route to full history. Repeated inspection work stays one record at time.

**Sam, accessibility-dependent user.** Dialog mechanics and field labeling are strong. Main failure is visual legibility: 8–10px metadata appears throughout operational rows. Long-form validation does not focus first invalid field, forcing keyboard and screen-reader users to search backward.

**Casey, distracted mobile user.** Bottom navigation and 44px coarse-pointer targets work. Two Fleet FABs compete in thumb zone. Add-vehicle form asks for many inputs and uploads in one scroll, with no draft indicator or interruption recovery beyond eventual global save.

## Minor observations

- "Updated now" is static copy, not timestamp or confirmed refresh state.
- Activity rows remain buttons even when their target record no longer exists; clicking then gives no feedback.
- Mobile filter is visually icon-only. Native select retains accessible name, but current filter value is invisible.
- Dark mode is thorough, though automatic OS switching may surprise crews expecting stable visual conditions.
- Missing `PRODUCT.md` limits audience and workflow validation. `/impeccable init` can capture that later.

## Questions to consider

- Should "Assigned" mean crew assignment exists, or can it represent external deployment without named crew?
- Is issue reporting more frequent than vehicle intake on phones? If yes, only issue action deserves persistent FAB.
- Does owner workflow center on resolving exceptions, maintaining records, or dispatching vehicles? Dashboard should pick one as dominant job.
